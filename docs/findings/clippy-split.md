# The clippy gate, split like the tests (2026-10-06)

`clippy` was one gate whose scope was the whole Rust tree, so no tree ever reused its verdict.
It is now two gates, generated by `cargo xtask test-shards` from the same layout as the test
shards (`.gatehouse/test-shards.toml`, `[clippy]`):

| gate | lints | scope | patterns | derives at HEAD |
|---|---|---|---|---|
| `clippy-libs` | the workspace minus the node packages (`--workspace --exclude …`), node crates stubbed; then `cargo clippy -p portcullis --all-targets` unchanged | test-libs's selection minus four absent-path probes, plus `clippy.toml` | 15 + 38 = 53 | yes |
| `clippy-node` | the node packages by name, `--no-deps` | the unsplit gate's scope | 19 | yes |

Both run under the shard runner's `--workspace-features`. The env, pins, seed, tools and resources
come from `.gatehouse/shards/clippy-base.json`, which is the unsplit gate's definition moved there.
Its workspace pass must equal the layout's `command` + `lints`, or the generation is refused.
`Clippy <- clippy-libs + clippy-node` in `ci/gatehouse-replacements.txt` declares that the two
gates took the context over together. Both list `Clippy` in `replaces`. Estimated saving, from the
counterfactual in gatehouse `docs/narrow-scopes-counterfactual-2026-10-06.md`: about +$6.40/week
net. It is not measured until a week of real runs.

## Nothing is linted less: measured, not assumed

**Measured** on this tree (6acbfa32f), macOS, by running the unsplit command and the two
groups' commands with `--keep-going --message-format=json`:

- **Compiled units.** The unsplit `cargo clippy --all-targets --all-features` and the two groups
  together compiled the same **381 workspace units**: (package, target, kind, features, test
  profile), **94 packages**, and no package is in both groups. The libs group finished in 1.2 s
  on the unsplit run's artifacts: every unit was already fresh, because workspace feature
  unification gives each member exactly the features the whole-workspace run did.
- **Diagnostics.** An injected `clippy::eq_op` in `nucleus-ifc` (libs) and `nucleus-spec` (node)
  produced the same three errors from the unsplit run as from the two groups together: two from
  clippy-libs, one from clippy-node, none missing or extra.
- **One crate is outside the measurement.** `nucleus-verifier-service`'s build script refuses a
  wasm built on macOS, because its pinned digest is the Linux build's. It failed identically in
  every variant. The lanes build it on Linux.

**Checked on every generation:**

- `clippy_packages_partition`: the libs group's `--workspace --exclude` set and the node group's
  `-p` set are exactly the workspace. A package linted by neither, or by both, is refused. Driven
  red: the "neither" test fails with the check disabled.
- The base's workspace pass equals the layout's command, so the split can't drift from the
  command the unsplit gate ran.
- CI-RP-2, which checks that every command a retired context ran is still run, now counts
  `--exclude`. A whole-workspace command is covered only if each excluded package is linted by a
  `-p` elsewhere in the declared gates. `Clippy <- clippy-libs` alone is red; the union is clean.

**The risk that remains:** a lint that fires only under a feature combination the measured tree
doesn't have. The unit sets are identical, so for this tree that combination doesn't exist. The
partition check holds the package sets equal on every future tree, and `--workspace-features`
holds the features. What's not re-measured on every tree is unit-set equality itself. That would
need the comparison above in CI, and it isn't there.

## Three wrong beliefs, each caught by checking

1. **That clippy-libs could reuse test-libs's scope as it stands.** It omitted `clippy.toml`, so
   the libs pod would have linted with no configuration, and its receipt would have been reused
   across a change to the lint policy. Added as `[clippy] reads`.
2. **That one more pattern was harmless.** test-libs's 56 patterns derive. 57, with
   `clippy.toml`, are refused `error[Capacity]` (gatehouse F-182), and a scope that never derives
   is never reused. That would have made the split pure cost. Four of the inherited patterns,
   `.env`, `.ssh`, `lib.rs` and `main.rs`, are runtime probes that test processes made of paths
   that don't exist. clippy runs no test, so `[clippy] drop` removes them. The generator refuses a
   drop that matches any tracked file, so only absent probes can be dropped.
3. **That CI-RP-2 could see what a split gate runs.** It couldn't, twice over:
   - **The runner.** Every runner-wrapped step parsed as `cargo run`, so the `cargo clippy` inside
     was invisible. CI-RP-2 now looks through `tools/test-shard` to the argv it execs.
   - **`--exclude`.** It was read as noise, so `clippy-libs` alone would have "covered" the
     whole-workspace command while linting no node crate.

   Both are fixed in `crates/ci-spec` and tested, driven red by disabling the exclude check:
   `rp_a_context_two_gates_took_over_together_is_clean_and_either_alone_is_red`.

## Not yet

- clippy-node's scope is the whole tree, as test-node's is, so it's reused only when nothing under
  `crates/**`, `tests/**` and the other Rust roots changes. All of the reuse is on the libs side.
- `measured_ms` is the unsplit gate's 1,152 s for each group. It's an upper bound until the first
  lane runs measure each group.

## clippy-node could not build its own runner (found 2026-10-07)

**What happened.** From #3278 until this fix, clippy-node failed on every tree it ran on. Its
step is `cargo run --manifest-path tools/test-shard/Cargo.toml -- cargo clippy …`, but its scope
was clippy-base.json's hand-written include list. That list predates the runner and never named
`tools/`. test-libs and clippy-libs get `tools/test-shard/**` from the layout's `global`, and
test-node's scope is `**`. clippy-node takes neither. Reproduced: materialize clippy-node's scope
at `2a360ad90` (1,917 files) and run the gate's argv. It fails with
``error: manifest path `tools/test-shard/Cargo.toml` does not exist``, exit 101.

**Why it stayed hidden.** The scope never changed, so the kernel derived the same hash on every
tree, and controld correctly REUSED the red verdict. #3291, #3287 and #3295 all showed
`clippy-node: verified but Failed ... reused from tree …`. Each looked like a defect in that PR.
#3287 was first diagnosed as its own `include_str!` of a file outside the scope. That defect is
real (docs/findings/compile-time-reads-in-scope.md, #3295), but it was not the only one. The local
reproduction ran `cargo clippy` directly, so it skipped the runner and saw only the second defect.
**The wrong belief: that a reproduction which leaves out the gate's wrapper reproduces the gate.**
Run the gate's argv as declared.

**Fix.** The generator gives clippy-node the runner's directory from `global`, the same place the
other shards get it. `manifests_covered` refuses any generated gate whose steps name a
`--manifest-path` whose tracked files the scope does not hold, and
`every_committed_gate_holds_the_manifests_it_runs` checks the committed definitions from
test-node. That test was driven red on `2a360ad90`'s clippy-node.json first: it named
`tools/test-shard/{Cargo.lock,Cargo.toml,src/main.rs}`. Over the regenerated scope (1,920 files),
the gate's argv builds the runner and lints. On macOS it exits 0 with `-p nucleus` left out, since
that crate's landlock code is Linux-only and is dead code on macOS.

**Cost.** clippy-node goes from 19 to 20 patterns and from 3,332,773 to 3,390,534 reduction rows,
80.8% of the kernel's MAX_ROWS of 2^22, measured with `gate scope witness --check` at gatehouse
`cb55244` with certificate sizes printed. The other three shard scopes are unchanged, and all
four derive.

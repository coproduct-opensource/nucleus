# Gap analysis — Clause 1: "any model"

North-Star clause under review: **"any model"** — the runtime must be usable by any model, vendor, or agent framework (including non-LLM automation and multi-agent trees) with *equal* guarantees. Date: 2026-09-08. Static reading of `/home/user/nucleus` and `/home/user/gatehouse`; nothing built, nothing modified. Every code claim below was re-read in the tree (line refs are from this checkout), not taken from the internal maps.

## 0. Framing: what "any model" has to mean for a security runtime

"Any model" is not a branding requirement. It is a *trust-boundary* requirement with four consequences, each of which the SOTA reports make concrete:

1. **The model process must sit below the enforcement boundary, not beside it.** Sandlock, Codex cloud, E2B, Kubernetes Agent Sandbox, and Anthropic's own sandbox-runtime all put the agent *inside* the sandbox and mediate at the syscall/socket layer (sota-isolation-attestation §2, §6: "the model is never trusted, only its mediated effects"). If the boundary is a flag on a vendor CLI, the guarantee is a property of that CLI, not of the runtime.
2. **The wire interfaces must be protocol-shaped, not product-shaped.** MCP (2026-07-28 spec, RFC 8707 audience binding), A2A v1.0 signed cards, AuthZEN 1.0 (PEP→PDP with MCP-tool and approval profiles), Claude/Codex/Gemini hook contracts (sota-agent-protocols §1, §3, §6).
3. **Authority arrives in the framework's own format** (OAuth scope/RAR, ID-JAG, txn-tokens with `act`, AP2 mandates, TOML/JSON rule files) and must be verified and *intersected* into one monotone element (sota-agent-protocols §6.1; sota-authz-tokens §6.6).
4. **Subagents, non-LLM workers and cross-runtime peers are principals too**: "Delegation Without Trust" (arXiv 2609.00267) — a compromised sub-agent's reach must be bounded by the task; SPIFFE practice is to derive child identity from the parent's attestation rather than pre-register (sota-authz-tokens §3).
5. **Model agnosticism must be *evidenced***: metrics per ≥3 vendors + one open-weight model, because FIDES/CaMeL/PACT shift 10–20 points across models (sota-agent-security-research §5.5).

Against that bar, nucleus's *kernel* (portcullis lattice, IFC discharge, LatticeCertificate, SPIFFE identity, `credentials.env`) is genuinely vendor-neutral and well engineered. The gap is almost entirely in what sits *between* the kernel and the model — the runner, the wire adapters, the authority ingress, the subagent story — and in the absence of any evidence that a second vendor works at all.

## 2. The gaps (ranked by how much closing them would expand safely-delegatable agency)

### GAP-1 — The model process is never beneath the boundary; the boundary is one vendor CLI's flag/hook contract (architectural, critical, large)

**What is wrong.** In Tier 1 and Tier 2 alike, the agent process runs on the operator host as `claude` with `--dangerously-skip-permissions`, and nucleus's *only* hold on it is that the CLI honours `--disallowedTools`, `--allowedTools`, and an exit-2 `PreToolUse` hook (`run.rs:1022-1062`, `mediation.rs`). `MediationGuard` (`run.rs:960-1002`) is a typestate proof that the *allowlist* is well-formed; it cannot prove the CLI obeys. Tier 2 confines the tool-proxy, not the model (`run.rs:664-746` spawns the CLI after the pod is up; `workload: None` at `run.rs:655,772`). A different vendor's CLI — or the same vendor's CLI after a flag rename — has no boundary at all. The in-guest `WorkloadSpec` path that *would* put any agent binary under `env_clear`/uid-drop/vsock mediation (`workload.rs:352-392`) is not driven by any shipped runner and gives the workload only a raw HTTP URL + HMAC secret (`workload.rs:130-146`), so an MCP-speaking agent inside the guest has nothing to connect to.

**SOTA.** sota-isolation-attestation §6: the credible TCB is KVM + jailed VMM + host-side effect supervisor, with the agent *inside*; Sandlock's split (static kernel policy carries authority, narrow supervisor carries decisions); Codex cloud, E2B, k8s Agent Sandbox, Anthropic sandbox-runtime all run the agent inside the sandbox. sota-agent-protocols §3: every coding-agent permission model admits its model-facing layer is advisory and "the OS sandbox is the only layer that survives a hostile model".

**Direction.** Make "agent inside the pod" the default Tier-2 shape and demote the host-side vendor launch to `examples/`: (a) `nucleus run --agent <cmd…>` populates `WorkloadSpec` with the agent binary (any CLI) and the prompt; (b) ship an in-guest stdio MCP endpoint by building the tool-proxy with `--features mcp` in the rootfs overlay (it already exists with the correct `args` schema and skips HMAC because stdio ⇒ guest, `mcp.rs:9-10,60-62`), and finish its #1216 migration so it is on the sealed effect path; (c) the workload gets `NUCLEUS_MCP_STDIO=…`/a Unix socket (`--listen-unix` exists, `main.rs:93-94`) instead of a bearer secret; (d) keep `--disallowedTools`/hook as defence in depth only; (e) add a boot-gated falsifier "workload cannot reach the network or filesystem except via the proxy" (the egress/workload probes already exist). Then the vendor CLI is just a `WorkloadSpec.command`.

### GAP-2 — The universal channel is broken: the shipped MCP `run` tool cannot deserialise at the proxy (implementation, critical, small)

**What is wrong.** `nucleus-mcp` — the MCP server every runner and every third-party MCP client (Claude, Codex, Gemini CLI, Cursor) would use — declares and posts `{"command": "<string>"}` (`nucleus-mcp/src/main.rs:94-96, 875-882, 1170-1181`), while the proxy's `/v1/run` accepts only `{"args": [...]}` with no serde alias (`tool-proxy/src/main.rs:891-905`; its own tests use `args`). Every exec through the default path is a 4xx. Fail-closed, but "any model can do useful work" is false for exec on the default path, for *every* model. The in-proxy rmcp server has the right schema but is compiled out by default and built by no workflow (`Cargo.toml:18-23`). Two MCP servers, one broken and one dark. Separately, the runner never grants `create_pod` (`run.rs:1068-1098`), so `manage_pods` is unreachable through MCP even when the profile allows it.

**SOTA.** MCP 2026-07-28 is the lingua franca; the maintainers' own guidance is that guarantees come from "network controls or sandboxing", i.e. exactly the proxy — which makes the proxy's MCP face the product.

**Direction.** Collapse to one MCP implementation: delete `nucleus-mcp`'s request types and depend on a shared `nucleus-api-types` crate that the proxy's HTTP handlers and both MCP faces deserialise through (one `RunRequest{args}`); or make the in-proxy rmcp server the only server. Add a contract test that spins up the proxy and drives every MCP tool through it (exec included), and run it in `ci.yml`. Grant `create_pod` in `build_mcp_allowed_tools` when `manage_pods ≥ LowRisk`.

### GAP-3 — No protocol-shaped decision API or adapters; the only hook is the vendor CLI's and the real hook lives in a private repo (architectural, high, medium)

**What is wrong.** A framework that is not the one vendor CLI has no way to ask nucleus "may this tool call proceed, and with what modified input?" The proxy exposes only effect endpoints (`main.rs:2100-2124`); the "hook" is `nucleus mediation-hook`, a `mcp__nucleus__*` name allowlist (`mediation.rs:65-90`) in one CLI's stdin/exit-2 contract; `--hook` mode and `nucleus guard` shell out to `nucleus-claude-hook`, which is private (`Cargo.toml:83`, `constants.rs:36`, `docs/quickstart-hook.md:6`). `portcullis::hook_adapter::classify_tool` hard-codes one vendor's built-in tool names and substring-guesses MCP names (`hook_adapter.rs:31-80`) and has no production caller. The Python SDK's "framework integration" is a pure-Python kernel with no parity test (`sdk/python/nucleus/kernel.py:1-9`).

**SOTA.** AuthZEN 1.0 (final Jan 2026) with MCP Tool Authorization and Access Request/Approval profiles; Bedrock AgentCore Policy fronting every tool call with a Lean-verified engine; Gemini CLI TOML policy engine (`argsPattern`, `mcpName`), Codex `approval_policy`, Claude hooks returning `permissionDecision`/`updatedInput` (sota-agent-protocols §1.1, §3, §4; sota-authz-tokens §4). The protocols report's interface #2 is exactly "a PreToolUse-compatible hook endpoint (allow/deny/ask/updatedInput), an MCP-aware proxy, an A2A responder".

**Direction.** Add `POST /v1/decide` in AuthZEN 1.0 shape (`subject`, `action`, `resource`, `context` → `decision`, `context.obligations`, optional `updated_input`) backed by `Kernel::decide_term_with_flow` and the IFC flow graph, callable over stdio/Unix socket from inside the pod; ship thin in-tree adapters: a generic `PreToolUse` JSON hook (re-implementing the private hook's public contract), a Gemini `ask_user` hook, a Codex approval shim, and a Python `ToolGuard` wrapper for LangChain/OpenAI-Agents/LlamaIndex that calls `/v1/decide` instead of reimplementing the kernel. Replace `classify_tool` with a configurable, per-framework tool→effect map whose *effect* is what is authorized (see GAP-8). Delete or parity-test `kernel.py`.

### GAP-4 — No authority ingress from other ecosystems: the proxy accepts only SPIFFE-mTLS or a shared HMAC (architectural, high, large)

**What is wrong.** "Any framework" arrives carrying its ecosystem's authority object — an OAuth 2.1 token audience-bound per RFC 8707, an ID-JAG assertion, an RFC 8693 `act`-chained transaction token, a RAR `authorization_details`, an AP2 Intent/Cart mandate, or a Claude/Codex/Gemini rule file. Nucleus's proxy admits none of them: `AuthTier` is mTLS, drand-approval, host-vsock, or HMAC (`auth.rs:584-602`). The node re-roots *nucleus* certificates from mTLS peers (`pod_authority.rs:31-38`), and the OIDC provider *emits* `act` (`oidc-provider/src/issuer.rs:77-81`), but nothing on the effect path consumes a foreign token and meets it into the lattice. `docs/wimse-aims-conformance-gap.md:29-32` still lists `typ`, `client_id`, `scope`, `act` as open. Only the Cart Mandate is modelled (`nucleus-recompute/src/cart.rs`). Consequence for clause 1: a Codex/Gemini/enterprise orchestrator cannot hand nucleus the authorization it already holds; it must be re-expressed by hand as a profile.

**SOTA.** sota-agent-protocols §6.1 ("Grant ingress: verify and *intersect* any authority object into one monotone lattice element"); MCP 2026-07 RFC 8707 + 8693 per hop; sota-authz-tokens §6.6 ("interoperate at the edges via OAuth plumbing, not as the internal carrier … convert them into the root block of a chain").

**Direction.** A `grant_ingress` module in node/proxy: (1) verify `at+jwt` bearer with `aud` = pod SPIFFE id via `nucleus-oidc-core` JWKS; (2) map `scope`/`authorization_details` to a lattice element through a declared, tested table (unknown → `Never`); (3) meet it with the pod certificate and record the foreign token's hash as `provenance` on a new authority block; (4) accept `act` chains as delegation hops. Add a Claude/Codex/Gemini rule-file importer that compiles `allow/ask/deny` rules into a `ProfileSpec` (deny→Never, ask→obligation, allow→LowRisk/Always) with a conformance corpus per format.

### GAP-5 — Subagent and multi-agent trees are not first-class (architectural, high, large)

**What is wrong.** Three separate holes. (a) *Intra-process subagents* (a vendor `Agent` tool, LangGraph subgraphs, OpenAI Agents handoffs) are invisible: the vendor `Agent` tool is simply denied (`constants.rs:21`); everything a framework spawns in-process shares the pod's one cert, one `SignedTaskRef`, one flow graph — no per-subagent attenuation is possible. (b) *Cross-pod spawn as an effect* is a stub (`AgentSpawnEffect for RealEffects` → `NotImplemented`, `portcullis-effects/src/lib.rs:767-776`); `spawn_agent` is a lattice dimension with no route. (c) *Cross-pod spawn via `manage_pods`* is well built at the node (child cert one hop below parent, `BudgetLedger`, IFC gate — `pod_authority.rs:24-56`, `pod_mgmt.rs`) but the runner never grants `create_pod` (`run.rs:1068-1098`), and `strip_requested_workload` (`pod_mgmt.rs:707`) means a child pod has no agent inside — it is an API with no worker. There is no A2A responder in the proxy; the A2A server is an example that verifies cards but does not attenuate authority.

**SOTA.** "Delegation Without Trust" (arXiv 2609.00267): confused deputy, token replay, injection escalation, compromised sub-agent; with defended delegation a compromised sub-agent's reach is bounded by the task. SPIFFE practice: derive child identity from the parent's attestation, avoiding pre-registration (sota-authz-tokens §3). Biscuit third-party blocks and UCAN invocation for per-hop narrowing (sota-authz-tokens §6.1-6.2).

**Direction.** (1) Implement `spawn_agent` as a real effect: `/v1/spawn_agent` = `create_sub_pod` with an attenuated child cert *and* a `WorkloadSpec` = the parent's agent binary with the sub-task prompt (relax `strip_requested_workload` to "same admitted binary, narrower policy"), returning the child SPIFFE id and streaming its receipts back as lineage edges. (2) Intra-pod: allow a framework to request a *sub-token* (`SignedTaskRef` chain attenuation already exists, `taskref_token.rs`) per subagent and present it per request (`x-nucleus-task-token`), so the kernel meets per call; a subagent that never presents one is bounded by the pod ceiling. (3) An A2A `AUTH_REQUIRED`/card-verifying responder in the proxy that maps a caller's signed card + delegation cert to a session. (4) Grant `create_pod` in the runner; parity-test child-cert depth and budget conservation end to end.

### GAP-6 — Vendor neutrality is declared broadly but enforced on two crates; load-bearing defaults still name one vendor (implementation, medium, small)

**What is wrong.** `steering.toml:15-21` declares a block-severity regex over all `.rs/.md/.toml` — and nothing consumes `steering.toml` (grep finds no runner). `ci/no-vendor-strings.sh` scans two OIDC crates by default (`:30-33`; workflows call it only there). Leaks that survive: `NetworkSpec::default().dns_allow` includes `api.anthropic.com` in the core spec crate, pinned by a unit test (`nucleus-spec/src/lib.rs:379,1659`) — every pod that does not override `network` gets one vendor's API as default egress, which is both a neutrality leak and a covert-channel default (a hostname allowed for every pod is an exfil path for every pod); `examples/podspecs/safe-pr-fixer.yaml:24`; `action.yml:14,76-80` (a GitHub Action that installs one vendor's CLI and defaults its model string); `nucleus-github-oidc/src/token_exchange.rs:7`; `guard.rs:240-247` `@anthropic-ai/` allowlist; `Cargo.toml:24`. `CLAUDE.md` itself forbids exactly this.

**SOTA.** Trivial; the point is hygiene. sota-formal-oversight A-conclusion 4: enumerate and ratchet the trusted/allowed set from source, let the count only shrink (gatehouse A-20 pattern).

**Direction.** Run `no-vendor-strings.sh` over `crates/ sdk/ examples/ action.yml` with a checked-in `vendor-allow` ledger (path:line:reason), and a shrink-only count in `scoreboard.json`; remove the model API host from `NetworkSpec::default` (orchestrator adds it via PodSpec; or a generic `model_api_hosts: Vec<String>` the orchestrator fills); parametrize `action.yml` with `agent-cli`/`agent-install`/`model` inputs and no vendor default; move `examples/claude-settings` and the private-hook docs under `examples/vendor-integrations/`.

### GAP-7 — No evidence that any second model, vendor or framework works: zero multi-model conformance or eval coverage (measurement, medium, medium)

**What is wrong.** The red-team harness is vendor-agnostic in its env (`LLM_API_URL/KEY/MODEL`, `red_team_harness.rs:58-61`) but runs one backend per nightly (`red-team-agent.yml:98-103`); AgentDojo is inert (`defense.py:96,110`); `production-delta.md:82` "Not started"; `scoreboard.json` and the north-star ledger carry no model/framework/vendor dimension (`north-star.md:667` is a bullet, not a clause); `tests/red_team_live.sh` needs `claude` + the private hook; the only "framework SDK" kernel (`sdk/python/nucleus/kernel.py`) has no Rust parity test. Clause 1 is therefore asserted, not measured.

**SOTA.** sota-agent-security-research §5.5: "every metric reported for at least three vendors' models and one open-weight model, because the frontier claim is about the runtime, not the model"; §5.7 cross-architecture comparison on a shared AgentDojo harness. FelonyBench-style violation rates under a real runtime (sota-formal-oversight B4).

**Direction.** An "agent conformance kit": one in-VM `WorkloadSpec` per (agent CLI × model backend) — at least two vendor CLIs, one open-weight model via an OpenAI-compatible endpoint, and one non-LLM worker — driven through `flow-replay` corpora and a revived AgentDojo bridge that calls the real kernel over `/v1/decide` (GAP-3) instead of a mirror; publish per-cell benign utility / utility-under-attack / ASR; add `frameworks_covered`, `models_covered`, `open_weight_covered` to `scoreboard.json` as grow-only ratchets; delete `kernel.py` or bind it with a Rust-generated verdict fixture like `kernel_vs_mirror.rs`.

### GAP-8 — The authorization vocabulary is coding-assistant-shaped; non-LLM automation and other frameworks must contort into it, and gatehouse's model-free `Cap` is a second, unrelated lattice (architectural, medium, large)

**What is wrong.** The 13 `Operation`s and the `Intent` enum (`nucleus-sdk/src/intent.rs:19-42`: ResearchWeb, CodeReview, FixIssue …) describe what one kind of assistant does, not what an effect is. `PolicyManifest.toml:32` authorizes `["Read","Edit","Write","Bash","Grep","Glob"]` — one vendor's tool names — as the repo's constitutional capability set. `classify_tool` maps unknown tools to `RunBash`. A cron job, a CI gate, a webhook worker or a Gemini/Codex agent has no effect-level way to declare "read `src/**`, write `target/**`, connect `api.example.com:443`, no secrets" and be admitted iff ≤ ceiling. gatehouse already has that vocabulary (`Cap = Σ(net)(exec)(wall)(cpu)(mem)(fsRead)(fsWrite)(secrets)`, `prelude/ci.writ:51-73`, semantic glob subsumption, `check_sound` in Lean) but it is CI-specific, duplicated in Rust, and not embedded in `PermissionLattice` in either direction (read-gatehouse §6 "neither proven to embed in the other"). `WorkloadSpec` carries no declared capability at all — the pod ceiling is the only bound, so a non-LLM workload cannot be least-privileged below the profile.

**SOTA.** Sandlock: static, input-independent kernel policy (paths/ports) carries authority; the supervisor carries per-call decisions (sota-isolation-attestation §2). ScopeGate/PACT: authorize *values* (destination, amount, path), not tool names (sota-agent-security-research §2.6, §2.8). Gatehouse's proof-carrying plan: `So (admissible_b plan policy) = oh` checked by a verified row-local kernel.

**Direction.** Introduce an effect-level `Cap` in `nucleus-spec` (fsRead/fsWrite globs with semantic subsumption, net host:port set, exec class, secrets set, resource bounds) that a `WorkloadSpec` or an MCP tool manifest declares; admission = `Cap ≤ ceiling` decided by a checker with a parity/embedding proof to `PermissionLattice` (a Galois connection like `cert_bridge.rs` already does for the 4-dim market lattice); port gatehouse's `globSubsumes` primitive and golden fixtures; treat `Operation` as a *derived* classification for the LLM-tool path, not the authorization vocabulary. This lets nucleus be the executor gatehouse's ledger rows A-9/A-10 are missing, and lets any non-LLM worker be a first-class, least-privileged principal.

- OIDC-provider `act` emission without consumption — covered by GAP-4.

## 4. Summary

The kernel is vendor-neutral; the *runtime experience* is single-vendor and cooperative: the model runs on the host under one CLI's bypass flag (GAP-1), the one universal channel (MCP exec) is broken on the wire (GAP-2), other frameworks have no decision API and the real hook is private (GAP-3), foreign authority cannot enter (GAP-4), subagents are either forbidden or stubbed (GAP-5), the neutrality invariant is unenforced and leaks into `NetworkSpec::default` (GAP-6), no second model has ever been shown to work (GAP-7), and the vocabulary itself is assistant-shaped rather than effect-shaped, leaving non-LLM automation and gatehouse outside (GAP-8). Closing GAP-1 + GAP-2 + GAP-3 alone would turn "any model" from a design intent into a testable property; GAP-5 and GAP-8 are what would let *trees* of models and non-model workers be delegated to with the same guarantees.

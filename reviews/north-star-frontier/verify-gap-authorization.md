Date 2026-09-08. Skeptical re-read of every cited file/line in /home/user/nucleus and /home/user/gatehouse. Static only; no builds, no edits.

## Method
For each gap: (a) re-read the cited lines, (b) grep both repos for the thing claimed missing under any name, (c) look for partial substitutes in other crates (node, spec, receipt, art12, lineage, gatehouse), (d) decide verdict + corrected impact.

## G1 — op-named counter approvals, dead HTTP path, unattributed, self-serviceable → CONFIRMED (critical)
Evidence re-read and accurate:
- `ApproveRequest{operation, count, expires_at_unix, nonce}` main.rs:921-929; `ApprovalRegistry{approvals: Mutex<HashMap<String,_>>}` main.rs:629-631.
- mediation.rs:161-190: `RequiresApproval` returns before `sandbox.write`; comment says "/v1/approve grant does NOT satisfy this layer (#2406)". main.rs:3105-3122 corroborates and documents the double consume.
- approve_operation main.rs:4319-4351: `actor: ActorIdentity::Unknown`; signature `_headers: HeaderMap` — the handler never reads the AuthContext at all, so the verified approver key cannot reach the record even in principle.
- escalate.rs:176-210 mints `EscalationGrant`, records a verdict, returns JSON; `grep kernel|attenuat|grant_approval escalate.rs` → nothing. `EscalationGrant` is consumed only by escalation.rs and escalate.rs.
- kernel.rs:1747-1750 `grant_approval(op, count)` unauthenticated; 2025-2033 `consume_approval(op)` keyed on op only; decide_term lowers to `(operation, subject)` (kernel.rs:1516-1518).
- nucleus-mcp main.rs:1072, 1382-1398: `/dev/tty` `Approve operation '{}'? [y/N]` on the op name.
- sdk/python session.py:138-160 + client.py:154-160: `Session.approve` POSTs `/v1/approve` itself; sdk auth.py only implements HMAC.
- main.rs:845 `max_uses.unwrap_or(usize::MAX)`; approval_bundle.rs:359-470 verify() checks alg/typ/jwk match/sig/iat/exp/manifest_hash only — no jti dedup, drand_round, attestation_hash.
Counter-evidence (nuance, not refutation):
- The route has a pinned-key Ed25519+drand approver tier (`NUCLEUS_APPROVAL_TRUSTED_KEYS`, main.rs:150-151, 387-390; auth.rs:486-500) that makes HMAC unreachable when configured. So "self-serviceable" is true for the legacy HMAC config and for the Python SDK (HMAC-only), not for a proxy started with approver keys. The finder's headline holds because the approval is still an op-name counter and still not consumed on the http_kernel_decide path.
- Preflight `ApprovalBundle` is manifest-bound (manifest_hash), which is a partial action binding at pod granularity.
Verdict: confirmed, critical.

## G2 — no revocation / kill-switch below fleet lockdown; validity extendable → CONFIRMED, impact HIGH (not critical)
Accurate: verify_certificate steps 1-6 (certificate.rs:1344-1440) have no revocation input; `grep -i revok` over certificate.rs/token.rs/kernel.rs/pod_authority.rs/tool-proxy → nothing (the repo-wide hits are OIDC key rotation, doc comments, and IFC "hard-to-revoke" naming). escalation.rs:177 promises revocation propagation with no field. verifier.rs:319/tls.rs:319 skip CRL/OCSP. lockdown_client.rs flips an AtomicBool; main.rs:2402 gates requests on `is_locked && !is_allowed_during_lockdown`.
Corrections:
- Lockdown is not fleet-only: node main.rs:3688-3745 scopes All/PodId/LabelSelector, and it is authz-gated (`authorize_grpc_operation(.. CancelPod)`). `cancel_pod` (node main.rs:3428, pod_api.rs:206) is a per-pod hard kill. So an in-fleet kill-switch exists at pod granularity.
- `TimeLattice::extend` (time.rs:130-132) has exactly one caller and it is a unit test (time.rs:219). A child block with a widened window fails `leq` at verify step 4c and the per-block `not_after` check 4d; kernel re-checks `TimeExpired` on every decide (kernel.rs:1159). "Validity can be extended" is overstated.
What remains genuinely missing: revoking an issued, offline-verifiable carrier (LatticeCertificate/AttenuationToken/SignedTaskRef/ApprovalBundle) held by a party outside this node's lockdown stream — external re-rooted callers (pod_authority case 2), tokens minted by `nucleus token delegate`, CLI-held certs. Those have expiry only. Impact high: TTLs bound the window, and pods on this node can be killed, but a principal cannot retract one delegation without either waiting or locking a scope.

## G3 — authorization language cannot say what principals mean → CONFIRMED (high), with a stronger finding
Accurate: certificate.rs:454-504 `subset_check` is exact string equality; portcullis-core delegation.rs:215-232 uses `glob_covers`; preflight uses `starts_with || glob_match` (action_term.rs:571-574) — three containment semantics. kernel.rs:1125-1128 `decide(op, subject:&str)`; decide_term lowers to that. profile.rs:46-96 ProfileSpec = capabilities+obligations+paths+budget+time; CEL `constraint` module is consumed only by profile.rs/lib.rs/tests (the `PolicySpec` used by nucleus-spec/tool-proxy/node is Profile|Inline lattice, not CEL). nucleus-cli token.rs:80-115 delegate takes profile/identity/expires_hours only.
Counter-evidence (partial): a principal CAN say "only host X / URL glob Y" at the PodSpec level — `NetworkSpec{allow, deny, dns_allow, url_allow, mime_allow}` (nucleus-spec lib.rs:313-345) and `credentialed_egress` — and the host-minted session task token carries `allowed_operations` (+ `allowed_paths` glob, deliberately empty: session_mint.rs:36-41). These are pod-config knobs, not delegation-carrier caveats, and none reach `delegate()`/`verify_certificate`.
Stronger finding (missed by finder, see M1): `SinkScope` is never authored anywhere — every minting site passes `SinkScope::unrestricted()`.
Verdict: confirmed, high.

## Missed gaps
M1 (high) — SinkScope is dead in practice: no authoring path. All minting sites pass `SinkScope::unrestricted()`: nucleus-node pod_authority.rs:351, 419, 448 (`mint_child_with_scope_using_key(.., SinkScope::unrestricted(), ..)`), nucleus-cli token.rs:302. `grep sink_scope` over nucleus-spec/src, nucleus-node/src, nucleus-tool-proxy/src (excluding the IFC declassify sink-scope, a different concept) finds no field a principal can set. The certificate primitive (`delegate_with_scope`, certificate.rs:843-860) and verifier step 4c2 exist, but no principal can ever produce a scoped block. So the only per-target attenuation in the carrier is unreachable — worse than G3's "exact-string" complaint.
M2 (high) — Approver roster bypass on the mTLS tier. `select_auth_tier` (auth.rs:609-626) gives `SpiffeMtls` precedence over `ApprovalEd25519Drand`, and main.rs:2510-2530 follows it; `approve_operation` (main.rs:4319-4323) takes `_headers` and never inspects the AuthContext or `check_identity_policy`. The MtlsListener admits any client cert chaining to the trust bundle (mtls.rs:13, 284) with no allowed-SPIFFE-ID filter (`grep allowed_spiffe|allowed_client` → nothing). Consequently any workload in the trust domain that can reach the proxy's mTLS port can grant approvals without holding an approver key — the pinned roster only constrains non-mTLS callers.
M3 (medium) — The host-minted session carrier cannot express paths, and approvals are volatile. session_mint.rs:36-41: `allowed_paths` deliberately empty ("Path scoping is the NEXT gating brick"); so the per-session SignedTaskRef, which is the only authority object injected on a host-controlled channel (session_token.rs), scopes operations only. ApprovalRegistry and ApprovalNonceCache are `Mutex<HashMap>` (main.rs:629-640) with no persistence: grants and nonce-replay state vanish on proxy restart (replay window bounded by MAX_APPROVAL_TTL_SECS=300).

## Overall
Six confirmed (G1, G2, G3, G4, G7, G8), two partially-addressed (G5, G6). No gap refuted. Impact corrections: G2 critical→high (per-pod cancel + scoped lockdown exist; extend is test-only and caught by leq), G5 high→medium (node ledger already conserves). Missed: SinkScope never authored (M1), mTLS bypass of the approver roster (M2), task-token path scope + volatile approvals (M3).

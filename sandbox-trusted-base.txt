# sandbox-trusted-base.txt — everything a nucleus pod's isolation boundary rests on.
#
# WHY THIS FILE EXISTS
#
# The 2026 sandbox-escape literature can report "94.4% of agents are vulnerable"
# because almost nobody can enumerate what their sandbox trusts. A TCB is only
# meaningful if it is written down: the classical definition says components
# belong in it only if they are *specifically designed* to govern security, and
# that judgement cannot be made about a set nobody has listed.
#
# Each line is one component of the guest-to-host boundary, and each carries
# either the test that pins it or an explicit UNPINNED with a reason.
# `scripts/check-sandbox-trusted-base.sh` verifies that every named test ACTUALLY
# EXISTS in the tree — a manifest whose references are not checked is prose — and
# ratchets the UNPINNED count so the unpinned set can only shrink.
#
# FORMAT
#   <component> | pinned_by:<test fn name>
#   <component> | UNPINNED:<why, and what would pin it>
#   <component> | EXTERNAL:<trusted third party we do not and cannot pin>
#
# ADDING A LINE IS ADDING TO THE TRUSTED BASE. That is sometimes right, and it is
# never free — the same accounting as `programmeTrustedBase` in the olog corpus,
# where adding a gate raises the number rather than lowering it.

# ── Not yet pinned. This is the honest part of the file. ────────────────────
vsock workload API request surface                  | pinned_by:guest_request_surface_is_exactly_three
vsock request surface cannot grow silently          | pinned_by:guest_request_surface_is_exhaustive
guest command frames are length-bounded             | pinned_by:oversized_frame_rejected_before_utf8_decode
an unknown guest command is rejected, not executed  | pinned_by:unknown_command_is_rejected_not_executed
guest pseudo-filesystems are nosuid/nodev/noexec    | pinned_by:guest_mounts_are_hardened
cgroup placement is applied before workload start   | UNPINNED:The CUTOVER IS DONE — the launch path now spawns the jailer (`--firecracker-jailer`, default true), which creates the cgroup and writes its pid into it BEFORE exec, and the post-spawn `apply_cgroup` is skipped when jailed. Every piece is unit-tested on Linux: the argv (jailer_applies_every_cgroup_limit_before_exec), the in-jail path rewriting (every_jailed_config_path_is_brought_into_the_jail), and the jail's real contents on a real filesystem (prepare_jail_creates_every_path_the_jailed_config_names). It stays UNPINNED because NOTHING IN-TREE RUNS A REAL FIRECRACKER: no test observes a booted guest confined by a cgroup that existed before it. Pinning needs an integration test on a Linux host with KVM. Until then this is a construction argument, not a measurement — and a construction argument is exactly what this column is not for.

# ── Trusted third parties. We depend on these and cannot pin them here. ─────
Firecracker VMM device emulation                    | EXTERNAL:AWS Firecracker. Five emulated devices by design; CVEs in its virtio implementations are outside our control and inside our boundary.
KVM / host kernel                                   | EXTERNAL:hardware virtualization is the isolation primitive; a KVM escape defeats everything above.
the seccomp filter file contents                    | EXTERNAL:the BPF program shipped at the filter path is trusted as written; we pin THAT it is applied, not WHAT it permits.
